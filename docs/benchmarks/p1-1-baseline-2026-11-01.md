# P1-1 baseline — engine v0.2 on the fixed corpus (measured 2026-11-01)

Measurement only, taken **before** any P1-1 engine work, against the
pre-registered gate in `docs/plan/03-phase-1-engine-repair.md` (P1-1). These
are the v0.2 numbers the future v0.3 run must be compared against, on the
same corpus. Nothing in the engine was changed to take them.

## Environment and method

- Machine: Linux/amd64 VM, 4 vCPU Intel Xeon Platinum 8321HC @ 1.40 GHz,
  ~8 GB RAM, otherwise idle during the runs. `GOMAXPROCS=4`.
- Go 1.26.7. Engine under test: `acl-exact/v0.2` (current `EngineVersion`).
- Default limits: 2 s / 2,000,000 operations / 50,000 boxes.
- Corpus: the fixed v0.2 corpus generator (`corpusACL`/`corpusCases` in
  `internal/verify/measure_test.go`, seed = rule count), reused unchanged,
  plus the two cases P1-1 registers but v0.2 lacked (`append_rule`,
  `change_last`; constructions below).
- Harness: `internal/verify/p11_baseline_test.go` (test-only; skips unless
  `PLENILUNE_P11_OUT` is set). 5 runs per case; ops and allocated MiB were
  identical in all runs and in a second full pass; wall medians of the two
  passes differ by at most ~9% (shared-VM noise), so **ops is the primary
  metric**; times are only comparable within one machine.
- Metrics: `Budget.Operations` / `Budget.PeakBoxes` from the Compare report
  (the engine's own counters charged against the caps), verdict +
  `SearchComplete` + `Budget.StopReason`, wall time per run, and allocated
  MiB per run (MemStats TotalAlloc delta / runs — the v0.2 method; it is
  cumulative allocation, not peak RSS).
- Raw data: `p1-1-baseline-2026-11-01.json` (pass 1, the table below) and
  `p1-1-baseline-2026-11-01-run2.json` (pass 2, stability check) beside
  this file.

## Calibration against the recorded v0.2 numbers

The original harness (`TestMeasureCorpus`) was re-run unmodified on this
machine first. Every shared case reproduces the recorded v0.2 ops, peak
boxes and allocated MiB **exactly** (e.g. identical-100: 96,894 ops, 6,664
peak boxes, 5.41 MiB — the known v0.2 figures). Wall time does not transfer
(33.2 ms median here vs 7.5 ms on the Windows 8-CPU reference machine);
ops/boxes/allocation do. The corpus and counters are therefore trustworthy
for the before/after comparison the gate requires.

## Added cases (constructions)

- `append_rule`: one new rule
  (`permit tcp host 192.0.2.200 host 203.0.113.200 eq 8443`) inserted
  immediately before the final `deny ip any any` — operator-style append.
- `change_last`: action of the last generated rule (index n−2, immediately
  before the final deny) flipped permit↔deny. Rule count unchanged.
- `append_rule_to_512`: 511-rule base, after side exactly 512 rules — the
  largest append constructible, because the parser caps an ACL at 512 rules
  (`ciscoacl.MaxRules`).

## Evaluation against the pre-registered P1-1 gate

- **Identical-512 must complete — current engine FAILS this criterion.**
  INCONCLUSIVE, stop reason `boxes`, halted at 261,044 ops with 38,612
  peak live boxes. Every measurable 512 case (including `change_last`,
  whose shared prefix is 510 of 512 rules) dies at the *same* point:
  v0.2 builds both full permit sets before any delta logic runs, so the
  failure is independent of where the change sits. This confirms the
  plan's premise (`exactDelta` constructs both sets from scratch).
- **Late-change/append: ≥50% ops and median-time reduction (post-change
  criterion).** Baseline recorded: v0.2 spends ~100% of the identical-case
  cost on a single late change — append_rule = 100.2% of identical ops at
  100 rules and 100.1% at 250; change_last = 100.2% / 100.2%. v0.3
  targets implied by the gate: append_rule ≤ 48,567 ops (100) /
  ≤ 232,272 ops (250); change_last ≤ 48,532 ops (100) / ≤ 232,426 ops
  (250); median times likewise halved on the same machine. At 512 rules
  neither case completes today (append not even constructible at base
  512; the 511→512 append is INCONCLUSIVE at 692,840 ops / 46,073 peak
  boxes).
- **Insert-at-head: no more than 10% worse than v0.2 (post-change
  criterion).** Baseline: 105,291 ops / 34.6 ms median (100 rules);
  508,952 ops / 139.1 ms median (250 rules). The 512-rule instance is
  **not constructible** under the current parser cap (after side would be
  513 rules), so this criterion can only be exercised at ≤250 rules with
  this corpus and parser.

## Notes and limits

- No obligations-heavy variant is measured: P1-1 does not define one, and
  the v0.2 harness compares with `nil` conditions; this baseline does the
  same.
- Wall times are this VM's only. Cross-machine or cross-day comparisons
  must use ops (deterministic here) or re-measure both engines on one
  machine, as protocol §4 requires.
- The 511→512 append case halts much later (692,840 ops, 46,073 peak
  boxes) than the 512-base cases (261,044 ops, 38,612 boxes): the box
  population near ~512 rules is intrinsic to this corpus family, which is
  the quantity a v0.3 covered-union construction would have to keep under
  the 50,000-box cap for the completion criterion to pass. The baseline
  fixes the numbers; it does not predict the v0.3 outcome.
